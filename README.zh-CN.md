# go-p2pmesh

[English](README.md) | 简体中文

基于 Golang 构建的 P2P 网络架构。

同一份代码提供两种角色：**服务端**只做协调（发现、信令、房间状态、端口授权），**客户端**负责与
对端建立加密的点对点隧道，并通过虚拟网卡暴露给本机应用。

> 以下内容按设计构想叙述。代码正按阶段落地，当前"已实现／尚未实现"的划分见[实现进度](#实现进度)。

## 功能概览

- **一套代码，两种角色。** 服务端负责协调、客户端承载数据，两者出自同一模块、共用一套协议。
- **协调而不托管。** 服务端承担发现、信令、房间管理与 NAT 信息交换，永不转发业务数据，不处于
  载荷路径上。
- **加密的点对点隧道。** 对端之间直连，由 Noise IK 握手与握手后的传输密钥保护。
- **虚拟网卡。** 每个客户端通过跨平台 TUN 设备加入同一个 IPv6 ULA 内网，现有应用无需改动即可通信。
- **确定性的身份与寻址。** NodeID 由机器指纹派生，网状地址由 NodeID 派生；不需要中央分配器、不需要
  DHCP，任何对端都能独立算出同一地址。
- **按角色授权的信任。** 由 Ed25519 签发、携带 `client`、`bootstrap`、`root` 角色并与节点 Noise
  静态密钥绑定的节点证书；对无法运行根密钥交换的部署提供首次使用即信任。
- **UDP 数据面叠加 KCP。** 在 UDP 之上提供可靠有序交付与可调重传参数，TCP 作为最后手段回退。
- **NAT 穿透优先级矩阵。** IPv6 直连、标准 UDP 打洞、对称型 NAT 端口预测、TCP 同时打开，以及可选的
  TURN 中继兜底。
- **房间隔离。** 只有同一房间的成员才知道彼此的地址，成员关系因此是发现的边界，而不是一个标签功能。
- **端口访问控制。** 默认拒绝的规则在网状地址上发布虚拟端口，同时让真实的本地端口保持不可达。
- **服务器互联。** 引导服务器之间互相 gossip 服务器表，客户端只需一个可达地址，并能在故障时切换
  而无需重新配置。
- **跨平台。** 支持 Windows / Linux / macOS，无需 CGO。
- **可嵌入。** 两种角色都以 Go 包形式提供，供第三方集成。

## 架构

系统分为三层，各层的信任属性是刻意区分开的。

**控制面。** 引导服务器监听 TCP（默认端口 `29683`），负责发现、信令、房间管理与 NAT 信息交换。
它是唯一被要求拥有稳定公网地址的组件，客户端在网络变化后也经由它重新接入。关键在于**控制面不在
载荷路径上**。

**数据面。** 对端之间通过 UDP 直接交换流量，其上叠加 KCP 以在不可靠数据报之上提供可靠有序交付，
并允许调节延迟与带宽的取舍。TCP 仅作为 UDP 端到端完全不可用时的回退。对于无论如何都无法打通的
组合，可选启用 TURN 中继作为最后手段。

**虚拟网卡。** 每个客户端创建一个跨平台 TUN 设备（Linux 为 `/dev/net/tun`，macOS 为 `utun`，
Windows 运行时加载 `wintun.dll`），并为自己分配一个统一 IPv6 ULA 前缀内的地址。应用之间通过该
接口通信，自身无需任何改动。

**硬性约束：引导服务器永不转发业务数据。** 它不创建 TUN 设备、不作为数据面对端加入网络、也不参与
打洞。这样协调点的运营方被彻底排除在数据路径之外：即使服务器被入侵或运营方有意窥探，能看到的是
谁在何时与谁通信，而不是传输了什么。中转即使发生，也属于另一个可选角色，且只转发不透明密文。

## 设计取舍

**为什么用虚拟网卡做覆盖网络。** 另一种做法是代理或要求每个应用接入 SDK，前者需要逐个应用改造，
后者把访问控制挪到了用户态。在应用之下放一个三层接口，意味着现有软件无需修改即可通信，而策略可以
施加在地址与端口上，而不是应用身份上。

**为什么用确定性的 IPv6 ULA 寻址。** 网状网络没有天然的位置去跑一个 DHCP 等价物，而中央分配器
既会成为瓶颈也会成为单点故障。把地址从 NodeID 派生出来，分配就变成一个纯函数：任何对端在隧道建立
之前就能算出目标地址，且在重启后保持稳定。`/64` 也为后续按房间或按服务划分子网留出了空间。

**为什么用 UDP 叠加 KCP 而不是 TCP。** 在丢包严重、经打洞建立的路径上跑 TCP 隧道会遭遇队头阻塞，
其拥塞窗口恰好在网状网络所要应对的场景下崩塌。裸 UDP 避免了这一点，却把可靠性推给了应用。KCP 处在
两者之间：提供可靠有序交付，同时把重传与窗口参数暴露出来，使传输层能按路径的真实丢包特征调参。
TCP 被定位为回退而非与 UDP 并列的选项，因为它是最后手段，而不是一个等价选择。

**为什么用 Noise IK 握手。** `IK` 假定发起方已持有响应方的静态公钥，在第一条消息中就认证了响应方，
并在同一条消息中加密发起方自己的静态公钥。这与网状网络的现实吻合——对端在连接之前就已经从控制面
获知彼此公钥——同时无需额外往返即可对被动观察者隐藏身份。密码套件为 `25519/ChaChaPoly/BLAKE2s`。

**为什么证书要分角色。** "任何客户端都可以充当服务器"是一封邀请中间人攻击的请柬：在没有授权机制的
情况下，谁能比真服务器更快应答，谁就成为服务器。由根密钥签发、且与节点 Noise 静态密钥绑定的证书，
使对端能够验证某个自称子引导服务器的节点确实被授权持有该角色。对于无法运行根密钥交换的部署，则提供
首次使用即信任。

**为什么中继是可选的独立角色。** 中继容量是网状网络中最稀缺、最容易被滥用的资源，也是第三方唯一能
经手两个对端之间流量的路径。把它默认关闭、从引导服务器中剥离、并限制为只转发密文，意味着默认部署
中不存在任何能读取载荷的中央组件。

## 控制协议

报文由 8 字节头部（大端 `uint32` 消息类型 + 大端 `uint32` 载荷长度）与最多 16 MiB 的 JSON 载荷
组成：

```
+----------------+----------------+---------------------+
| type (4 bytes) | length (4)     | JSON payload (N)    |
+----------------+----------------+---------------------+
```

当前阶段刻意选择 JSON 而非 protobuf，以避免引入代码生成步骤；分帧与载荷编码相互独立，因此后续若要
切换编码，不影响连接处理逻辑。

| # | 消息 | 方向 | 用途 |
| --- | --- | --- | --- |
| 1 | `HELLO` | 客户端 → 服务端 | 上报 NodeID、公钥、可选证书与协议版本。 |
| 2 | `CHALLENGE` | 服务端 → 客户端 | 返回 32 字节 nonce、服务端证书与服务器表快照。 |
| 3 | `AUTH` | 客户端 → 服务端 | 承载 Noise 握手消息。 |
| 4 | `AUTH_OK` | 服务端 → 客户端 | 认证成功，下发分配的 IPv6 地址与引导对端列表。 |
| 5 | `NAT_PROBE` | 客户端 → 服务端 | 上报探测到的 NAT 类型、公网地址、可选公网 IPv6 地址，以及用于对称型预测的端口采样。 |
| 6 | `NAT_RESULT` | 服务端 → 客户端 | 确认 NAT 信息，并代为转达对端的 NAT 信息。 |
| 7 | `PUNCH_REQ` | 客户端 → 服务端 | 请求目标节点的打洞信息。 |
| 8 | `PUNCH_INFO` | 服务端 → 客户端 | 返回目标公网地址、NAT 类型、预测端口区间与同步开火时间戳。 |
| 9 | `KEEPALIVE` | 双向 | 心跳，携带 Unix 时间戳。 |
| 10 | `PEER_LIST` | 服务端 → 客户端 | 周期性推送在线节点及其地址、NAT 类型与所属房间。 |
| 11 | `ROOM_MEMBERS` | 服务端 → 客户端 | 推送房间成员列表。 |
| 12 | `ROOM_JOIN` | 客户端 → 服务端 | 请求加入房间，可带密码。 |
| 13 | `ROOM_LEAVE` | 客户端 → 服务端 | 离开当前房间。 |
| 14 | `PORT_RULE_SYNC` | 服务端 → 客户端 | 下发适用于该客户端的端口访问规则。 |

`PUNCH_INFO` 中那个同步时间戳，正是让两个对端无需额外协商即可在同一瞬间开始发包的关键：由服务端
而非任一対端决定打洞何时开始。

## 身份与信任

一个节点的身份由三部分构成：

| 组成 | 派生方式 | 用途 |
| --- | --- | --- |
| NodeID | 机器指纹的 SHA-256，base32，26 字符，`8-4-4-4-6` 分段 | 稳定、可人工转写的名称，同时是地址派生的输入。 |
| Ed25519 密钥对 | 本地生成 | 签名，以及证书链的根。 |
| X25519 密钥对 | 本地生成 | 握手中使用的 Noise 静态密钥。 |

NodeID 大小写不敏感，限定为 `[a-z0-9-]`，且不允许出现在首尾或连续出现连字符，因此可以安全地用作
文件名、数据库主键或 URL 路径片段。此外还提供以 X25519 公钥的 SHA-256 作为次级指纹，便于做密钥固定。

证书把 NodeID、X25519 公钥、角色（`client`、`bootstrap`、`root`）与可选有效期绑定在一起，由根
Ed25519 密钥对恰好包含这些字段的规范字节编码签名。校验时用证书内嵌的签名者公钥验证该签名；启用首次
使用即信任后，未签名的首次接触会被接受，并记住该公钥以供后续连接使用。

## NAT 穿透

穿透遵循固定的优先级矩阵，从代价最低、最直接的方式向后排列：

| 优先级 | 策略 | 适用条件 |
| --- | --- | --- |
| 1 | `ipv6_direct` | 双方都有可用的 IPv6 链路，无需打洞。 |
| 2 | `udp_standard` | 双方都是锥型 NAT，一个出站包即可打通。 |
| 3 | `udp_predict` | 至少一侧处于对称型 NAT 之后，需要预测映射端口。 |
| 4 | `tcp_simultaneous` | UDP 端到端不可用，需要 TCP 同时打开。 |
| 5 | `turn_relay` | 无法建立直连且已配置中继。 |

对称型 NAT 是难点：由于外部端口随目的地址变化，双方无法得知面向对方时会使用哪个端口。应对方式是
端口预测——采样已观察到的映射以推断分配规律——配合在预测区间内的同步并行发包。这本质上是尽力而为，
效果取决于该 NAT 的端口分配策略是否具有可预测性。

分类所用的 NAT 类型为 `Open`、`FullCone`、`RestrictedCone`、`PortRestricted`、`Symmetric` 与
`Unknown`。项目只实现 STUN 客户端，从不在本地运行 STUN 服务器，而是依赖第三方公共服务器。

## 房间

房间是隔离单元，而不是聊天频道：只有同一房间的成员才会被告知彼此的地址，因而也只有它们才会尝试建立
隧道。房间成员关系就是发现行为的授权边界。

房间包含 ID、显示名、属主、`encrypted` 标记与成员上限。服务端管理器与客户端成员缓存是两件独立的
事：客户端只保存最近一次被通知的成员集合，并对加入、离开、更新三类推送做出反应。

## 端口访问控制

默认策略为拒绝。在该策略下，发往未配置端口的流量被拒绝，只有显式配置的规则被放行。另一种策略
是允许，语义反转，放行一切未显式配置的端口——只有在完全可信的房间内才适合使用。

规则把**虚拟端口**（对端访问目标节点网状 IPv6 地址时使用的端口）映射到目标机器上的**本地端口**。
控制器对两者都建索引，因此能回答两个不同的问题：某个虚拟端口的入站连接是否被允许，以及某个本地端口
归哪条规则所有。这是有意为之：对端无法通过访问真实本地端口来触达服务，只有虚拟映射可达，从而使
映射层成为网状网络与主机之间一道真实的边界，而不是一层便利封装。

## 服务器互联

引导服务器之间自成一个网状结构，使客户端只需知道一个可达地址。服务器表保存每个已知服务器的地址、
公钥、ID、最近可见时间、负载以及是否为根节点。表项按 TTL 过期，由两个循环维持其新鲜度：周期性全表
gossip 轮次，以及清理超时表项的扫描。客户端在 `CHALLENGE` 响应中获得该表的快照，在 `AUTH_OK` 中
获得对端列表，因此无需重新配置即可切换到其他服务器。

## 目录结构

```
cmd/
  server/       服务端二进制：命令行参数、配置、服务安装、信号处理
  client/       客户端二进制：同上，另加房间与隧道相关参数
internal/
  protocol/     控制面消息类型与长度前缀分帧
  crypto/       Noise IK 状态机、Ed25519 密钥、证书签名
  identity/     机器指纹、NodeID 派生、密钥持久化
  config/       INI 加载、默认值、校验
  bootstrap/    控制面服务端与客户端连接逻辑
  servermesh/   服务器表与 gossip 循环
  room/         房间模型、客户端缓存、服务端管理器
  routing/      IPv6 到对端的路由表与路由器
  portcontrol/  端口访问规则与虚拟端口映射
  stun/         STUN 客户端与 NAT 类型体系
  holepunch/    打洞策略矩阵
  tunnel/       KCP+Noise 隧道与隧道管理器
  tun/          跨平台虚拟网卡抽象
  relay/        可选 TURN 中继
  storage/      Store 接口、SQL 后端、建表脚本
  api/          REST 管理 API 与中间件
  sysutil/      系统服务安装
pkg/
  server/       供第三方嵌入服务端的公开库 API
  client/       供第三方嵌入客户端的公开库 API
  types/        共享公开类型（NodeID、Room、地址、身份）
```

`internal/` 与 `pkg/` 的划分是有意的：`pkg/` 是受支持的第三方嵌入接口，而 `internal/` 可以随时
变更而无需事先通知。

## 构建

```bash
go build -o gop2pmesh-server ./cmd/server
go build -o gop2pmesh-client ./cmd/client
```

交叉编译无需 CGO：

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o gop2pmesh-server ./cmd/server
```

## 使用

```bash
# 使用默认配置启动服务端
gop2pmesh-server

# 指定配置文件
gop2pmesh-server -c /etc/gop2pmesh.ini

# 使用默认配置启动客户端
gop2pmesh-client

# 指定引导服务器
gop2pmesh-client -bootstrap 203.0.113.10:29683
```

两个二进制都支持 `-install` 安装为系统服务、`-uninstall` 卸载。

## 配置文件

两个二进制都通过 `-c` 指定 INI 配置文件，默认文件名分别为 `server.ini` 与
`client.ini`；文件不存在时使用内置默认值。`configs/` 目录下提供了带注释的模板。

### 服务端（`server.ini`）

`[server]`

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `host` | `0.0.0.0` | 控制面监听地址。 |
| `port` | `29683` | 控制面端口，用于信令与节点发现。 |
| `mesh_peers` | 无 | 需要互相同步的其他引导服务器，逗号分隔。 |

`[api]`

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 是否启用 REST 管理 API。 |
| `host` | `0.0.0.0` | API 监听地址。 |
| `port` | `29684` | API 监听端口。 |
| `cert_file` | `server.crt` | 提供 HTTPS 所用的 TLS 证书。 |
| `key_file` | `server.key` | 该证书对应的 TLS 私钥。 |
| `client_ca_file` | `clients_ca.crt` | 用于校验客户端证书的 CA（mTLS）。 |
| `jwt_secret` | 自动生成 | JWT 签名密钥；留空时首次启动自动生成。 |
| `token_ttl_hours` | `24` | 签发的 API 令牌有效期。 |
| `admin_user` | `admin` | 初始管理员账号，首次启动时创建。 |
| `admin_password` | 自动生成 | 初始管理员密码；留空时随机生成。 |

`[database]`

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `type` | `sqlite` | 取值 `sqlite`、`mysql`、`postgresql`、`mongodb`。 |

`[log]`

## 作为 Go 库使用

```go
import (
    "github.com/yourorg/go-p2pmesh/pkg/server"
    "github.com/yourorg/go-p2pmesh/pkg/client"
)

srv, _ := server.New(server.WithHost("0.0.0.0"), server.WithPort(29683))
go srv.Start()
defer srv.Stop()

cli, _ := client.New(
    client.WithBootstrap([]string{"203.0.113.10:29683"}),
    client.WithRoom("myroom", ""),
)
go cli.Start()
defer cli.Stop()
```

选项采用函数式风格：每个 `With*` 修改一个配置结构体，由 `New` 在构造任何子系统之前完成校验。传入
非法组合——没有引导服务器、MTU 小于 `576`、未知的端口策略——会在构造阶段直接失败，而不是等到首次
使用才暴露。
